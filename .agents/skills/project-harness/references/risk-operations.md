# Risk and operations

Read this reference when work has an external effect, elevated consequences, valuable mutable data, publication, continuous operation, notification, backup, or rollback.

## Permissions and risk

Scale controls to potential harm, reversibility, disclosure, and actual use. For each material risk record the dangerous scenario, safeguard, observation, and residual limitation. A risky branch does not stop independent safe work.

Ask for missing authority immediately before spending, installing, publishing, externally delivering, performing a destructive action, or transferring sensitive data. Do all authorized reversible preparation first. Tool access itself is not permission.

An instruction is not a technical security boundary. When integrity depends on permissions, isolation, protected CI, a signature, professional review, or external approval, say so and use that control when required. Another model's agreement is not independent professional approval.

## Data

Separate source and static materials, mutable user data, Harness state, and evidence. Git and Harness history are not database backups. Keep secrets and unnecessary sensitive values out of prompts, state, logs, evidence, notifications, and delegated tasks.

For valuable mutable data, define acceptable loss, backup destination, retention, access, cost, and restoration. Obtain authority for new storage or transfer. Before a risky change, create an applicable recovery point when required. Test restoration in isolation; the existence of a backup file is not evidence of restorability.

## Incidents and notifications

Report a material failure discovered during active work even if a later retry succeeds. Distinguish detection, send attempt, successful delivery, and recipient acknowledgement.

A continuously operating product requires an actual monitoring and notification mechanism only when active requirements or agreed risk call for it. Test the channel and event path. A finite document or design is not continuously monitored by this Skill.

Notifications contain the affected system, observation time, current status, impact, action taken, and required user action without secrets or unnecessary sensitive data.

## Release and rollback

Before a consequential release, define a safe rollback or explain why rollback is unavailable. A rollback plan identifies the exact version or operation, trigger, allowed actions, preservation of new data, and success checks. Rolling back code does not imply rolling back a database.

Automatic rollback is permitted only by a previously authorized specific plan. Otherwise prepare the action and obtain the missing authority. Verify the resulting product and data, not merely the command exit code.

Project Harness does not promise unattended maintenance. Future updates start through the user or a separately configured and authorized runtime mechanism.
